# Report on technology review and selection

This report provides a review of web technologies, graphics application programming interfaces (APIs), graphics libraries and graphics engines from the perspective of their applicability to 3D astronomy visualization and ease of implementation or integration. Based on the advantages and disadvantages of existing technologies, we select a subset to be used for developing the client side of Gaia Explorer.

Astronomy visualization differs from conventional 3D graphics (based on surfaces and polygon rasterization) in several aspects. The data may consist of a large number of astronomical objects, each associated with coordinates, brightness, spectral measurements, classifications, uncertainties, or other attributes. The data can be sparse, heterogeneous, and much larger than the available system or graphics memory. These characteristics necessitate the use of specialized approaches to data representation, querying, and transfer to the end devices.

Additionally, as per the project requirements, Gaia Explorer will support data processing operations, such as grouping, filtering, and mapping. These requirements imply that rendering will represent only a small part of the system, and special attention must be given to the processing and architectural aspects of the reviewed technologies, including data representation, memory management, and general-purpose computing on the GPU (GPGPU) capabilities.

For this review, we selected a representative subset of the technologies that most directly fit our use case, and examined each one from different perspectives, including rendering, data processing, adoption, and ease of development and maintenance. Our selection covers both low-level and high-level technologies, ranging from graphics APIs to game engines and visualization libraries. These technologies are not necessarily interchangeable: WebGL and WebGPU are APIs, while Three.js, Babylon.js, and similar projects are libraries or engines built on top of graphics APIs.

## Review of selected technologies

### Low-level graphics APIs

#### WebGL 1.0

WebGL 1.0 exposes and API based on OpenGL ES 2.0. For this reason, it was easy to integrate into most modern web browsers, and remains important for older systems with less capable hardware. However, it lacks most features of modern GPUs and the API itself is rather outdated. Its main limitations are as follows:

- **No compute shaders.** WebGL 1.0 does not have general-purpose compute capabilities, compute shaders or storage buffers. It is possible to emulate this functionality using render-to-texture techniques, but under strong limitations for data layout and format choices, and with a significant performance penalty. This approach is at best a specialized workaround rather than a foundation for a system such as Gaia Explorer.
- **Technical limitations.** It provides a very limited set of texture formats, buffer features, and rendering capabilities. There are no integer textures or shared memory.
- **Restrictive shading language.** The shading language is also very restrictive, most notably it does not support dynamic loops, recursion, bitwise operations, atomic operations and function overloading, and puts strong limitations on conditional branching.
- **Non-ubiquitous extensions.** It exposes a few modern functionalities that are available on the majority of current hardware through API extensions. These extensions are often not ubiquitous and their pervasive use can severely limit the set of supported devices.
- **External standardization.** The standard is not a living web standard, as it is maintained by Khronos. Furthermore, the standard relies on other standards (most importantly OpenGL ES 2.0 and the supplemental specification for the shading language) that may change without the consent of web browser developers.

WebGL 1.0 is suitable for conventional 3D graphics applications with triangle rasterization, lighting, texturing, and basic post-processing, but general-purpose computation and advanced rendering techniques require a newer, more capable graphics API. We choose not to target WebGL 1.0 as a primary backend for its lack of support for critical GPU features.

#### WebGL 2.0

WebGL 2.0 is a more modern graphics API similar to but much more capable than WebGL 1.0. It is based on OpenGL ES 3.0 and introduces several significant improvements over its predecessor. It adds support for 3D textures, integer texture formats, uniform buffer objects, multiple render targets, instanced drawing, and transform feedback. These capabilities make it possible to use WebGL 2.0 for certain advanced rendering techniques and for less demanding GPGPU tasks.

However, similarly to WebGL 1.0, WebGL 2.0 does not support compute shaders and storage buffers. Although certain computational tasks can be implemented through render-to-texture techniques as in WebGL 1.0, the API imposes significant restrictions on data access, memory layout and supported texture formats, and can impose significant performance overhead.

Two techniques can be used to perform GPGPU without native compute shaders: **render-to-texture** and **transform feedback**. For both techniques there are libraries that significantly simplify their practical use.

In render-to-texture, input and output data is stored in textures, and a fragment shader is used to sample the input textures and write the result of the computation to the output textures. Stateful computation can be achieved by swapping input and output textures between iterations. This approach is limited by texture formats and the number of supported input and output textures. Output is limited to the same fragment. Arbitrary buffer access and variable-length outputs are not possible. This matters because scientific computation often requires operations that are not naturally rendering operations.

In transform feedback, input data is stored in vertex buffers, and vertex shader outputs are redirected to output buffers instead of being forwarded to the rasterization and fragment processing stages of the graphics pipeline. Stateful computation can be achieved by swapping input and output buffers between iterations. The approach is limited by the data layout and supported vertex formats, as well as the number of input and output buffers. Arbitrary buffer access and variable-length outputs are not possible.

Apart from the lack of GPGPU features, WebGL 2.0 also suffers from similar disadvantages as WebGL 1.0:

- **No explicit memory management.** WebGL 2.0 has limited memory management capabilities. It does not support storage buffers, shared memory, or explicit memory management. Custumized data layouts and access optimizations are therefore not possible.
- **Restrictive shading language.** Its shading language remains restrictive with many of the same limitations as its predecessor. It uses GLSL ES 3.00, which introduces several improvements over its predecessor, including integer operations, bitwise operations, and more flexible control flow. However, its feature set remains tied to the conventional 3D graphics pipeline. It does not support arbitrary buffer access, atomic operations, or unrestricted load-store operations.
- **Modern features are not standardized.** WebGL 2.0 remains constrained by the extension model. Some essential capabilities are exposed through optional extensions, such as filtering and writing to floating-point textures. Their availability varies across browsers, drivers, and hardware, making WebGL 2.0 less attractive as a candidate for a scientific visualization backend.

WebGL 2.0 is still a reasonable choice for conventional 3D graphics, and specific use cases, which can benefit from the workarounds described above. It is a useful compatibility choice for applications that do not require specialized rendering techniques, fine-grained memory management and general-purpose computation, but the lack of such features makes it unsuitable for the use in Gaia Explorer.

#### WebGPU

WebGPU is the newest low-level graphics API and has been designed to support a common feature set of the most widely adopted desktop graphics APIs – DirectX, Vulkan and Metal. It combines graphics and general-purpose computation in a unified and explicit resource model. It exposes an API that is profoundly different from WebGL 1.0 and 2.0, which more directly aligns with the current hardware and can thus be significantly more performant for specific operations. It is supported in most major browsers and operating systems, but as it is a relatively new API, its support is notably less than for WebGL 1.0 and 2.0.

The programming model and API architecture of WebGPU more closely matches our requirements for Gaia Explorer. It supports general-purpose computation through compute shaders, provides more explicit memory management, and does not impose strong restrictions on buffer and texture usage.

WebGPU's main advantages are as follows:

- **Compute shaders.** WebGPU supports compute shaders that can read and write arbitrary buffer memory. Compute shaders can be directly used for mapping, filtering, and transforming the data, without resorting to the graphics pipeline. Consequently, such operations can be much faster, as graphics-specific operations such as rasterization need not be executed. In Gaia Explorer, compute shaders can be used for hardware-accelerated filtering and compaction, to compute histogram or density statistics, or prepare data for subsequent rendering operations.
- **Control over data layout.** Data can be laid out in a GPU buffer almost arbitrarily, subject only to hardware alignment and size constraints. Storage buffers have been designed to work with structured data, not only arrays of pixels or vertex attributes. A storage buffer can store positions, arbitrary attributes, visibility flags, and selected point indices, while the user has fine-grained control over the data layout. Compute shaders can then process these data without CPU intervention, which can significantly reduce unnecessary data transfers.
- **Predictable performance.** WebGPU uses explicit pipelines, bind groups and command encoders, which incur more upfront cost, but eliminate validation in run time. This allows for a cleaner separation between computation, rendering, data transfer, and synchronization, and makes the application's performance much more predicable while allowing explicit optimizations.
- **Modern and feature-rich shading language.** The WebGPU shading language (WGSL) provides a much wider feature set and is not nearly as restrictive as GLSL. It includes arbitrary buffer access, shared memory, atomic operations, and much more. The language is standardized by the same work group as the API, and it is published as a web standard, so its future evolution is much more predictable.
- **Asynchronous design.** Most communication between the API and the GPU is asynchronous, including data transfer and pipeline execution, which makes it possible to parallelize certain operations that would necessarily have to be executed serially in WebGL.
- **Headless execution.** In contrast to WebGL, compute work in WebGPU can be executed without a graphics frontend, which allows WebGPU to be run outside of a web browser, for example for testing purposes. A few major JavaScript runtimes already support WebGPU either natively or through libraries, including Node.js, Deno, and Bun.

However, WebGPU is not a universal solution. It has a few serious practical limitations, some of which we believe will be eliminated in the near future:

- **Limited support on some platforms.** Browser support is still not ubiquitous. Most major browser vendors have implemented WebGPU on Windows and MacOS, but support for Linux devices and mobile devices is still lacking or hidden behind experimental feature flags.
- **Verbosity prolongs development time.** Due to the verbosity of the API and the need for manual low-level resource management, development costs are higher. We believe that there are still benefits for this in the long run, but providing an initial prototype of an application may take a significantly longer time. Special care must be taken for optimizing data transfer and synchronizing execution, which was handled by the browser in WebGL, but in WebGPU it can lead to poor performance if not handled properly.

WebGPU is not a replacement for a good software architecture, but it can provide measurable improvements on for a relatively low effort on platforms that currently support it. Most importantly, a large dataset cannot be visualized interactively just by choosing a more modern graphics API. We believe that the set of supported features and their suitability for scientific visualization and data processing make WebGPU a suitable choice as a graphics backend, despite its relatively scarce support on less popular platforms.

### Graphics libraries and frameworks

#### Three.js and Babylon.js

Three.js and Babylon.js are two of the most widely used JavaScript libraries for 3D graphics. They provide scene management, cameras, materials, geometry, lighting, asset loading, interaction utilities, and a large collection of extensions. Both are mature engines for developing interactive 3D applications, and they specifically target ease of use and fast prototyping, especially for game development, by providing a set of abstractions for common use cases. They are both well documented and backed by a strong community and a large ecosystem of extensions.

Their main focus is conventional 3D rendering, so computationally intense workloads and rendering of large-scale point clouds and volumes are consequently pushed to the side track. Three.js supports a WebGPU backend through the newer and less mature WebGPURenderer interface, and can fall back to WebGL 2.0, which is the better supported option. Compute shaders are supported through the community-developed GPUComputationRenderer, which encapsulates the render-to-texture workflow described in the section about WebGL 2.0. Babylon.js, on the other hand, has native support for WebGPU and compute shaders, as well as a specialized solution for point clouds and point cloud rendering, which makes it a better fit for Gaia Explorer.

However, both libraries, despite being mature solutions with strong community support, have certain limitations, which discourage us from choosing them as the basis for developing Gaia Explorer:

- **Pervasive abstractions deteriorate performance.** The libraries are very large, as they purposefully abstract away many API-specific and platform-specific features. Such abstractions may incur significant performance overhead for performance-critical applications.
- **Different target audience.** Both Three.js and Babylon.js target conventional 3D graphics and have limited support for non-conventional rendering techniques and data representations such as point clouds. For example, the point cloud renderer in Babylon.js uses points mainly to support particle systems, and so the renderer only consumes positions and colors, and no other attribute can influence the rendering. The one and only rendering technique is too limiting for our use case and we would need to spend significant effort to extend the library and integrate new options, and the same holds for Three.js.
- **Integration overhead.** The scene graph, object management, material system, and other abstractions may be unnecessary for a renderer targeting large point clouds. These abstractions do not automatically benefit point-cloud-specific rendering and processing pipelines, and it is unclear whether such abstractions save enough development time to offset the work required to integrate specialized rendering techniques into existing libraries. Moreover, custom GPU data structures, streaming, scheduling, and rendering techniques still need to be developed as part of the project, and development may suffer due to integration overhead.
- **Engine constraints.** Engine conventions and automated resource management can become constraints if the application's architecture diverges significantly from the engine's intended use. Given that the engine does not include the functionalities we intend to develop out of the box, we would need to modify the chosen engine to follow our use cases.
- **Severely limited fallback.** Given the shortcomings of WebGL 2.0 described above, we cannot tolerate a fallback with severe technical and performance limitations. In light of this, we must discard Three.js from our technology selection.

In summary, these libraries are more attractive when conventional 3D graphics are required, but not the first choice for an application whose main purpose is scientific visualization of a large dataset. No existing feature set tailored for conventional 3D graphics is likely going to cover the requirements of Gaia Explorer. A set of purpose-built extensions can work around such limitations, but that reduces the benefit of adopting an existing engine in the first place. In the best case, the engine would have to be profoundly modified and extended, which would incur significant development overhead, and the solutions would have unpredictable performance. Additionally, these libraries are subject to change and long-term stability of Gaia Explorer would likely suffer from the constant changes.

Both Three.js and Babylon.js would be viable options if common functionality, such as camera controls, scene management, and conventional rendering techniques, provided substantial value compared to custom functionality. However, choosing an existing engine is less compelling as Gaia Explorer needs a specialized data-oriented pipeline with custom data management.

#### Vis.gl (deck.gl and luma.gl)

deck.gl and luma.gl are frameworks for high-performance visualization of large datasets in web applications. They are part of the vis.gl suite, which is explicitly designed for high-performance visualization, so it is one of the most relevant higher-level options to evaluate before committing to a custom renderer.

deck.gl is a high-level framework that provides reusable layers for rendering, filtering, and picking. deck.gl uses luma.gl as its underlying rendering infrastructure, which supports both WebGL 2.0 and WebGPU. The main advantage of this setup is usability, as it is possible to create complex interactive visualizations without having to resort to a low-level graphics API. The layered architecture supports adding custom layers, which can be a useful middle ground between a full-featured graphics engine and a low-level graphics API. For implementing custom functionality, luma.gl provides direct access to the GPU through WebGL 2.0 and WebGPU. High-performance data processing can be implemented this way.

Nevertheless, both libraries provide limited control over low-level rendering, and they are performance and memory constrained for large datasets such as those from Gaia. Specialized visualization techniques, such as the ones to be implemented in Gaia Explorer, will require custom layers, which will tightly couple the implementation to the API provided by the libraries. As with other existing graphics engines, the question is whether the existing functionality can offset the slower development due to API constraints.

Development can also be hindered by a work-in-progress integration of WebGPU. The latest deck.gl documentation explicitly states that WebGPU support is still a work in progress and is not production ready.

The libraries also have a steep learning curve, and their efficient use requires familiarity with the API. Specifically, the layer and rendering architecture has to be fully understood for them to be efficiently utilized. The developers on this project have not yet worked with these libraries, so a slower onboarding period is to be expected.

Furthermore, the examples provided with the frameworks are targeted toward geospatial data visualization, and their abstractions and data model do not seem to be optimal for large-scale astronomical data. Consequently, the functionality provided by the frameworks provides less value for our use case.

#### regl, ogl, glii, twgl, lightgl, etc.

Lightweight graphics libraries provide an alternative to higher-level frameworks and engines described above. They offer more direct access to the GPU while providing utility functionality for easier work with common pipelines. They allow developers to implement specialized rendering techniques quicker, while not completely abstracting away the underlying API, but rather emphasizing explicit GPU resources and functionalities. They deliberately avoid imposing higher-level structures, such as objects, cameras, materials, and scene graphs, and instead expose utility functions for developers to easily integrate such features if necessary. These advantages make lightweight libraries particularly interesting for developing Gaia Explorer.

The main drawback, and unfortunately one that renders these libraries unacceptable, is that they are targeting WebGL. To the best of our knowledge, no mature lightweight library exists for working with WebGPU, and as the API itself is much more user-friendly, such a library would provide little benefit over using the API directly.

Like the other general-purpose solutions, these libraries do not remove the need to develop specialized functionality. For a new application, a small in-house WebGPU abstraction would likely provide a cleaner long-term solution than adapting the libraries primarily developed for WebGL. The disadvantage is the increased implementation effort.

### Specialized visualization frameworks

#### VTK.js

The Visualization Toolkit (VTK) is a mature scientific visualization framework, which has been rewritten for the web and released as VTK.js. It is particularly relevant to the Gaia Explorer project because it is a specialized data visualization solution rather than a general-purpose graphics engine.

It supports a wide range of data types, including scalar fields, vector fields, tensors, textures, and volumes. Its strengths are most apparent when working with established visualization and processing techniques, such as volume rendering, slicing, and geometric processing. If such techniques were to be used in Gaia Explorer, VTK.js would be a strong candidate. Given that our use case necessitates specialized techniques, it is a less compelling choice.

Similarly to the majority of other technologies in this review, the foundational API used by VTK.js is WebGL, with WebGPU support described as preliminary. The documentation explicitly states that WebGPU support is still under development and applications using it may break as the API changes.

Our main concern is that the target workload is a highly data-intensive interactive visualization application, and a general scientific visualization toolkit is not necessarily optimized for the expected scale of the data. The framework's relatively low data processing speed has been brought up on several occasions, which is why it has been rarely used outside of the scientific community, and high-performance applications tend to choose alternative solutions.

#### Potree

Potree is a WebGL-based point cloud renderer for large point clouds. It uses a hierarchical structure to organize spatial data to support incremental loading, level of detail, and out-of-core rendering. These capabilities are aligned with the goals we set for Gaia Explorer, which makes Potree a highly relevant option to consider.

It provides and established architecture for hierarchical data management, streaming, and efficient point cloud rendering, and so it is a good starting point to develop an application such as Gaia Explorer, as we would not have to reimplement these functionalities from scratch. The included rendering techniques, however, are rather limited, and mostly target use cases involving human-scale data, such as agriculture, urbanism, cultural heritage, and environment engineering. These rendering techniques would have to be adapted and extended for astronomical visualization.

Potree is built on Three.js and consequently shares with it some of the advantages and disadvantages. Since Three.js is a stable and mature engine, Potree does not have to deal with the implementation details, and also regultarly receives performance updates. Building Gaia Explorer on top of Potree, however, would imply a rather long dependency chain, which can be very fragile when updates are propagated downstream. Direct GPU access and performance optimizations would be practically impossible without profound adaptations to both Potree and Three.js. Maintaining such adaptations would incur additional work in the long term. The same is true for adaptations to data management and level-of-detail mechanisms. Since Potree is open-source, we will aim to adapt the data management concepts to our needs.

Potree is especially valuable because it demonstrates that WebGL's limitations do not prevent effective point cloud visualization. However, since our use case involves significant data processing tasks, we believe that the lack of support for WebGPU and compute shaders would significantly reduce the performance of this part of Gaia Explorer.

#### CesiumJS

CesiumJS is a JavaScript framework for large-scale geospatial data visualization. Similarly to Potree, it is an out-of-the-box solution for large hierarhical point clouds, especially those than can be organized in tiles. The underlying 3D Tiles technology provides similar functionality as Potree, including hierarchical data organization, level of detail, and progressive loading. Its underlying concepts and architecture are relevant to Gaia Explorer in the same aspect as Potree.

A tileset in 3D Tiles consists of a hierarchy of bounding boxes with 3D content. This allows the client to determine the visible tiles and their required level of detail, so that the renderer can maintain interactive performance. The format supports different spatial data structures, including octrees, and different content types, such as point clouds and mesh geometry. This way the content, its representation and organization are separated from the rendering engine, which allows independent optimizations based on a specific dataset. These capabilities could serve as a useful foundation for hierarchical data management in Gaia Explorer.

For astronomy, however, CesiumJS's focus on geospatial data may be a bad fit. Units on the galactical scale span multiple orders of magnitude, distances are large, and precision requirements are much higher than for Earth-centered applications. Supporting such extremely large scales would require significant customization. Furthermore, the engine is based on WebGL, which, for the same reasons as with other WebGL-based options, we find too restrictive for high-performance data processing.

Even if CesiumJS is not adopted as the rendering framework in Gaia Explorer, 3D Tiles is worth considering as an interoperability format. Its representation of the bounding volume hierarchy and separation of content is highly applicable to data streaming and level of detail we planned for Gaia Explorer. A custom engine built on WebGPU could include similar functionality while introducing Gaia-specific metadata and coordinate systems. This would preserve the benefits of 3D Tiles while not sacrificing data-processing performance.

## Functionality categories

We separated the functionalities of Gaia Explorer into several categories, which allow us to separate data management concerns and precisely define what each reviewed technology covers and where its advantages and disadvantages lie. The categories are as follows:

- **Data layer**: Representation of coordinates and other attributes, metadata, compression, and quantization. This category also includes data access and storage, including streaming, chunking, level of detail, and buffering.
- **Data processing**: GPU compute capabilities, including querying, culling, filtering, mapping, and aggregation.
- **Rendering**: Point projection, rasterization, color mapping, culling, shading, and specialized rendering techniques (e.g., Gaussian splatting).
- **Visualization and interaction**: Camera interaction, spatial navigation, animation, annotations, and data selection and interaction.

The advantage of this separation is that the algorithms and data model can remain largely independent of the rendering, which is particularly important if the graphics APIs or libraries will have to be replaced or updated in the future.

### Data layer

The performance of a visualization application depends on the data layout and access patterns, and the ability to quickly answer visibility queries and filter data. For example, a renderer can draw 100 million points in a synthetic benchmark, but may still perform poorly on a real dataset, when a large proportion of additional processing comes from data transfer, attribute filtering, sorting, visibility queries, and user interaction.

The chosen technologies should ideally allow us to do manual memory management and to fine-tune the data layout based on our needs. The dataset should be prepared in a format that can be consumed by the GPU with minimal conversion and as efficiently as possible. For example, point attributes can be stored in separate arrays or buffers instead of interleaved structures, which may on some hardware architectures provide significant performance advantages. A structure-of-arrays layout can be beneficial when an operation needs few attributes at once. When more attributes are needed, an array-of-structures layout can avoid excessive memory fetching and improve cache efficiency.

Depending on precision requirements, data can be represented as integers, floating point numbers, with scale and offset, and they can also be compressed or otherwise encoded. Some modern technologies expose hardware encoding and decoding operations for specific formats, which may significantly improve performance for such operations.

Low-level graphics APIs generally provide all necessary tools to fine-tune the data layout and to split a large memory allocation into smaller chunks given additional alignment requirements. This is true for WebGL 2.0 and WebGPU, but not entirely for WebGL 1.0, which is rather limiting both in terms of memory management and data formats. Some lightweight libraries allow programmers to fine-tune the data, but this ultimately reduces the need for a library in the first place, as their main benefit is essentially to reduce such low-level work for a typical application. Graphics engines, specialized systems and higher-level libraries typically hide these details from the programmer for the benefit of portability, ease of development and maintenance, and graphics API abstraction.

Since we are building a data-intensive application our choices include **WebGL 2.0**, **WebGPU**, and specialized solutions that have been designed around point cloud data, including **Potree** and **CesiumJS**.

### Data processing

The most data-intensive operations must be performed on the GPU due to the sheer amount of data. These operations include but are not limited to mapping, filtering, sorting, and aggregation. Ideally, the chosen technologies would directly support GPU computation through compute shaders, but a fallback to the rendering pipeline can be a viable option for less demanding operations. Some operations, such as filtering and sorting, cannot be naturally encoded as rendering operations, so these operations become much slower. Consequently, we prioritize technologies that do not require such workarounds.

Filtering and aggregation can be performed on the GPU, but it is important to distinguish between testing objects with predicates and generating a compact list of filtered or aggregated objects. While a fragment shader can discard fragments based on a predicate, these fragments still need to be processed at every frame. Filtering a list of object into a compact list can completely avoid such redundant processing. A simple compute shader can generate a visibility bit per object. Turning a list of visibility bits into a densely packed index list, that can subsequently feed an indirect drawing command, may require a prefix sum, atomic operations, or another compaction method. This is not possible with a fragment shader.

For Gaia Explorer, we expect filtering and sorting to be the most practical data processing operations. Furthermore, we expect aggregation to be a common operation because of the required support for hierarchical level of detail. None of these operations can be efficiently performed in a fragment shader, so we will avoid technologies without support for hardware compute shaders.

In light of these facts, our choices include **WebGPU**, **Babylon.js**, and **Vis.gl**.

### Rendering

All graphics APIs, libraries, and engines support a set of hardware-accelerated rendering operations. APIs expose low-level primitives, while libraries and engines may implement higher-level concepts. For our use case, having the ability to develop specialized rendering algorithms hinges on the availability of low-level operations.

Working directly with an API, such as WebGL and WebGPU, can be beneficial for us because it allows us to design rendering pipelines as we see fit, without any restrictions imposed by a library or an engine. Lightweight libraries do not typically impose such restrictions because their purpose is only to facilitate API usage and not to abstract away any of its expressive power. Graphics engines, on the other hand, often provide a set of existing rendering techniques and sometimes a means to extend the existing functionality. Three.js and Babylon.js both allow users to develop custom rendering algorithms by writing custom shaders. They both include a preprocessing layer, allowing the shaders to utilize existing code provided with the engines. However, this may come at a cost of additional restrictions on the data layout and access, and it tightly couples the shader code to the engine, making it more difficult to migrate to another set of technologies in the future if the need arises.

From the low-level graphics APIs, we would not consider WebGL 1.0 for developing specialized rendering techniques, as it comes with severe restrictions on the available operations and data layouts. WebGL 2.0 and WebGPU, on the other hand, expose modern features, not only a limited subset targeting older and less capable hardware.

Specialized systems are the worst category in this aspect, as they typically do not expose the rendering functionality to the user, but rather provide a set of existing and to some degree configurable rendering techniques. Extending existing functionality would necessitate profound modifications to the system, requiring considerable effort and development time. We choose to avoid this possibility.

Our choices with regard to rendering are thus **WebGL 2.0**, **WebGPU**, and **lightweight libraries**. Slightly hesitantly we also include **Three.js** and **Babylon.js** in this list.

### Visualization and interaction

In this category, we discuss the user-facing functionalities, including the graphical user interface, interaction with the scene, camera control, and visualization parameters, as well as animation, and features related to visualization, such as annotation and data selection.

Unlike the previous categories, visualization and interaction are less concerned with the underlying graphics API and more with the abstractions and tools provided by the libraries. Implementing all interaction mechanisms from scratch is possible, but can require considerable effort. Libraries that provide these features can significantly reduce the development time, particularly when they can be extended with application-specific requirements of Gaia Explorer.

The reviewed technologies differ considerably in the level of functionality they provide. Low-level graphics APIs allow implementation of specific rendering techniques, but do not offer built-in camera controls, scene management, or user interface components. Most of these features would have to be implemented independently or provided by additional libraries. Lightweight libraries offer a more convenient starting point.

Graphics engines are the most feature rich of the selected technologies and naturally include functionalities for animation and interaction, as the vast majority of games and visualization applications need them. Three.js provides camera controls, ray casting, object picking, and a scene graph implementation, while still allowing substantial customization. Babylon.js provides similar functionality. Both engines can reduce implementation effort, although their abstractions may introduce tighter coupling between the architecture and the underlying systems.

Among specialized visualization systems, Potree includes interaction mechanisms specifically designed for large point clouds, including point picking, measurement tools, annotations, and specialized navigation controls. CesiumJS provides functionality for geospatial visualization, including camera navigation, terrain interaction, entity selection, and support for time-dependent visualization. These capabilities can substantially reduce development effort, but their predefined architectural assumptions may limit the flexibility required by Gaia Explorer.

Considering the requirements of Gaia Explorer, we prioritize technologies that provide flexible camera controls, efficient data selection, and customizable visualization parameters, without imposing restrictions on the rendering architecture. We therefore consider **Three.js**, **Babylon.js**, **Potree**, and **CesiumJS** as potential candidates. Direct use of graphics APIs also remains an option, although it would require implementing most of the user-facing functionality independently.

## Recommendation

Overall, given that the project aims to establish a strong foundation for future development, we recommend a WebGPU renderer with a clear architectural separation between the data layer, rendering layer, and user interface layer.
